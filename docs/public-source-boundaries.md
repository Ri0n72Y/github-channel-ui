# Public source entry points and host boundaries

- `client.ts`: browser-only Cordis plugins, ReactUIService, generic App({ui, children}), ThemeProvider/ThemeToggle, SessionMenu, resource helpers and repository access UI. App renders host-supplied children before registered routes; no HeaderBrand, initialPath or global Navigator.
- `domain.mjs`: pure domain exports, including githubResource.
- `server.mjs`: named Node-only business handlers, including OAuth/session/verification, repository and Issue reads/writes, config, channels and Topic. Never import this entry from client code. API endpoints dispatch to these handlers; the 11 Functions and 16 rewrites remain unchanged. Existing helper facades with consumers remain.

Plugins own resource paths: /:owner/:repo, /:owner/:repo/issues, /:owner/:repo/issues/:number, /:owner/:repo/issues/new, /:owner/:repo/config, /:owner/:repo/channels, /:owner/:repo/members, /:owner/:repo/members/register, /topic/:owner/:repo. Hosts own /. Real root URL input accepts exact repository/Issue/list/new Issue and the two main-branch config-file URLs. Public mounts its landing as a host-owned `/` route in the same real runtime as resource plugins. Ordinary repository links and entry guards share `resourcePath` / `repositoryLinkPath`: `api`, `assets`, `playground` are reserved top-level prefixes (case-insensitive); `/topic/:owner/:repo` has Topic precedence. A repository owned by `topic` can use the two-segment home and unambiguous four-segment Issue/member-registration paths, but its colliding three-segment ordinary config/channel/member/list links display an explicit unavailable state instead of navigating to another Topic. Topic-source paths remain independent. No query-selected legacy runtime. /playground/:slug uses explicit mock services for linked pages; selected-plugin isolated test mounting remains supported.

Repository reads run first; structured repository denials produce a page-local access notice. Session check precedes the protected installation probe. Successful reads do not add a probe. Retry repeats the original read, never a write. Issue pagination access denial retains the mounted previously read content, drafts and feedback, disables writing and paging, and recovery rereads the Issue plus first page without replaying a write. Topic public discovery has a distinct read policy (below); write checks remain server-side.

## Topic source and write contract

The only formal Topic route is `/topic/:owner/:repo`. GET `/api/topic-page` and `/api/topic-projects` bind to that exact public repository, not an arbitrary Topic slug. The two-segment path `/topic/example` is an ordinary repository path, not a Topic discovery route. Slug demonstrations belong to the explicit Playground fixture.

Read the source's default-branch snapshot and root `README.md`. The first Markdown H1 supplies the title (fallback: Topic Page); text after it supplies the description and optional email/datetime metadata. The root `topics.config.yaml` accepts flat scalar fields:

```yaml
topic: example-topic
whitelist: true
# Optional cover: an approved direct HTTPS GitHub raster image URL
```

The optional `cover` must pass the approved GitHub image URL grammar; raw.githubusercontent.com images require a full commit SHA. No implicit cover.jpg discovery. The parser rejects unsupported or duplicate fields, invalid values and invalid project declarations. Missing configuration displays an uninitialized state without searching; malformed or unavailable configuration reports an error, with no fallback to arbitrary searches.

The whitelist defaults to true. With it enabled, valid declarations directly under the root `projects/` directory (`.yaml` or `.yml`, case-insensitive extensions) contribute their sole `repository: owner/name` field; repository names are case-insensitive. A missing directory or empty valid set yields no projects. The directory may contain at most 50 entries matching these extensions, counted before filename, blob and declaration validation; exceeding this limit or using an invalid `projects` directory fails closed with HTTP 422, without truncation. Unsupported filenames, non-regular or invalid blob entries, and invalid parsed declarations are skipped. For eligible files, a read, size, encoding or blob-integrity failure fails the entire source snapshot; it does not return a partial whitelist. Only explicit `whitelist: false` skips declarations. Results are the configured public Topic search intersected with that set when enabled; the source itself is excluded. Neither the source nor candidates need App Installation or login for these public reads. Ordinary repository-resource reads retain the installed-public-repository access policy; anonymous fallback is limited to verified installed public resources.

The server returns one complete filtered GitHub Search page of up to 100 raw candidates, at offset zero; page 2 and later require the source HEAD. The client consumes 25-item slices, automatically fills sparse initial results and supports incremental loading, stable identity deduplication, cancellation and manual loading. The 10-page/1000-candidate Search window is distinct from true exhaustion; incomplete results, authorization/rate limits and failed source reads are not empty success. Source and Search success caches are bounded and process-local; explicit refresh and confirmed effective config writes invalidate their generation. Cache hits and request budgets are not guaranteed across instances.

Topic Config and Report are separate authenticated writes. Config requires explicit confirmation, current OAuth user/App repository authorization, Contents:write, reviewed HEAD/file SHA and effective branch rules on the actual default branch. Protected targets require the appropriate Pull requests:write grant and maintenance PR; pending PR content is not effective. Report requires a confirmed, short-lived target/actor-bound proof and rechecks current Issues:write authorization. Neither uses an installation token as a substitute for the OAuth user. Uncertain writes must be verified before retrying. See current implementation and [testing](testing.md) for failure cases.

## Build and release evidence

Use the reviewed full Git commit as the source identifier and maintain one React/ReactDOM/React Router/Cordis instance in the application. Keep the browser, pure-domain and server entry points separate. The published source is not an npm package release.

The current build uses Node 22 and npm installation of the versions/ranges in package.json. No dependency lockfile is tracked at this baseline; a Git SHA is sufficient to identify source, not to reconstruct the precise dependency tree or guarantee byte-identical output. For a reviewed build, retain the full Git SHA, Node/npm versions, exact resolved dependency graph (including transitive packages), generated lockfile if available, build/test commands and results, and output/deployment identifiers where applicable. On a fresh independent checkout, use the recorded lock with a compatible npm version and `npm ci` if a matching lock has been retained; compare results against the recorded evidence. Never change the normal CI install command solely to reconstruct history.

For dependency review, export the installed graph (`npm ls --all --json`) and package metadata (`npm query '*' --json`) from the actual reviewed installation, then inspect package license files and notices, including unresolved metadata. A manifest range or SPDX field alone does not establish the complete applicable license text or rights. Record the source retrieval and Corresponding Source delivery method for any network release. Preserve the known-good deployment/source identifiers and verify rollback eligibility before any Owner-authorized change. No package publication, release lock, licensing decision or deployment is implied by this document.
